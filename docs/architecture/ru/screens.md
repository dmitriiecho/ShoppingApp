# Экраны

[English version](../en/screens.md) · [Все разделы](README.md)

У экрана одно состояние UI, набор событий от пользователя и набор разовых эффектов. ViewModel превращает события в новое состояние или в эффект; экран только рисует состояние и реагирует на эффекты.

## Файлы экрана

На примере корзины (`feature/cart/impl/.../presentation/cart/`):

| Файл | Что в нём |
|---|---|
| `CartScreen.kt` | две перегрузки `CartScreen`, приватный `CartContent` и мелкие помощники вроде верхней панели |
| `CartViewModel.kt` | состояние, обработка событий, эффекты |
| `CartUiState.kt` | состояние и его вложенные типы |
| `CartEvent.kt`, `CartEffect.kt` | что делает пользователь и что происходит один раз |
| `components/` | секции со своими превью (`CartItemCard`, `CartTotalsCard`, …), `internal` |

### Две перегрузки вместо Route + Screen

- **Публичная `CartScreen(onBack, …, viewModel = hiltViewModel())`** собирает состояние и эффекты.
- **`internal CartScreen(uiState, snackbarHostState, onEvent, modifier)`** не хранит состояния и содержит `Scaffold`, поэтому её можно показать в превью без Hilt.

Навигационный код других фич в любом случае вызывает экран по одному имени.

### События идут только через файл экрана

`onEvent` доходит до экрана без состояния, до `CartContent` и до мелких приватных помощников. Секции из `components/` получают конкретные колбэки (`onRetry`, `onQuantityChange`), поэтому не знают событий экрана и показываются в превью сами по себе.

## UI state

```kotlin
data class CartUiState(
    val content: Content = Content.Loading,
    val isOpeningCheckout: Boolean = false,
    val isClearCartDialogVisible: Boolean = false,
) {
    sealed interface Content {
        data object Loading : Content
        data class Loaded(val items: List<Item>, /* … */) : Content
    }
    // ...
}
```

- **Один `StateFlow` на экран**: `combine` по источникам и `stateIn(WhileSubscribed(5_000))`.
- **Вложенные типы.** Типы, из которых состоит только состояние, лежат внутри `XxxUiState` и пишутся как `CartUiState.Item`. Внутри владельца имя не повторяется: `PromoCodeUiState.Check`, а не `PromoCodeCheck`.
- **Поля сгруппированы по секциям экрана**, а не идут плоским списком: у оформления это `order`, `address`, `paymentMethod`.
- **Загрузка — это состояние, а не флаг и не `null`**: sealed `Loading` / `Loaded` / `Error`, везде с этими именами. `null` значит только «неизвестно», например имя товара, которое не передала deep link.
- **Состояние хранит то, что экран рисует**, в том числе решения (`canAddOneMore`), а не доменные модели и не сырые данные.
- **Повторяющиеся условия — геттеры** состояния: `canCheckout`, `showsOrder`.

### Действия читают источники, а не состояние

`uiState` получает изменение только после `combine`, чуть позже. Проверка перед действием читает сам источник: «Оформить заказ» проверяет `isSubmitting.value`, иначе быстрый двойной тап оформлял заказ дважды.

## Эффекты

Навигация и снекбары происходят один раз, поэтому это эффекты, которые идут через `Channel`, а не часть состояния: состоянию понадобилось бы ещё одно событие «обработано». Экран обрабатывает их через [`ObserveEffects`](../../../core/compose-utils/src/main/java/krio/systemdesign/shoppingapp/core/composeutils/effects/ObserveEffects.kt):

```kotlin
ObserveEffects(viewModel.effects) { effect ->
    when (effect) {
        CartEffect.NavigateToCheckout -> navigate { onOpenCheckout() }
        is CartEffect.ShowSnackBar -> showSnackbar(snackbarHostState, effect.message.asString(resources))
        // ...
    }
}
```

- **Собираются, пока экран виден** (`STARTED`). Эффект, отправленный в фоне, ждёт в канале и обрабатывается, когда пользователь вернётся.
- **На `Main.immediate`.** Эффект обрабатывается прямо внутри `send` ViewModel'и; если бы между ними была пауза, экран, остановившийся в этот момент, забрал бы эффект и потерял его.
- **`navigate { }` выполняется, только пока экран сверху** (`RESUMED`), и это не даёт двойному тапу перейти дважды.
- **`showSnackbar` работает в своей корутине**: снекбар ждёт, пока его закроют, и задержал бы следующий эффект.
- **Один эффект снекбара на экран**, `ShowSnackBar(UiText)`: ViewModel собирает текст из строкового ресурса, не имея доступа к ресурсам.

## Поля ввода

Текст поля — это `TextFieldState`, который создаёт ViewModel и кладёт в состояние одним и тем же объектом на весь экран:

```kotlin
private val searchQuery: TextFieldState = savedStateHandle.savedTextField(KEY_SEARCH_QUERY)
```

- **Нет события `OnTextChange`.** Поле меняет состояние на месте, поэтому ввод никогда не ждёт flow и не теряет символы: старая схема `value` + `onValueChange` теряла их при быстром наборе.
- **Значения, выведенные из текста, — геттеры** состояния (`canApply`). Compose отслеживает это чтение.
- **`snapshotFlow { state.text }` во ViewModel — для действий**: поиск, сброс ошибки после правки.

## Сохранение состояния

То, что пользователь ввёл или открыл, переживает смерть процесса; то, что делал запрос, — нет.

| Переживает | Как |
|---|---|
| текст в полях | `savedStateHandle.savedTextField(key)` |
| открытый диалог, выбранный вариант | `savedStateHandle.getStateFlow(key, default)` |
| страница каталога, на которой был пользователь | номер страницы в `SavedStateHandle`; список открывается на ней |
| результаты запросов | не хранятся: экран загружает их заново |

## Стабильность Compose

Strong skipping включён, поэтому по умолчанию ничего не размечается:

- **По умолчанию без `@Stable`, `@Immutable` и `ImmutableList`.** Composable пропускается, если получает тот же объект.
- **Источник преобразуется до `combine`**, чтобы объект менялся, только когда меняется его источник: оформление делает `observeCart().map { it.toOrder() }`.
- **Модели из `:shared:domain` для Compose нестабильны** (этот модуль собирается без компилятора Compose), и аннотаций Compose там нет. Где это важно, экран получает свою UI-модель на простых значениях: `CartUiState.Item` в корзине.
- **Колбэки списка принимают id элемента** (`onQuantityChange: (productId, quantity) -> Unit`), поэтому все карточки получают одни и те же лямбды, и «+» перерисовывает только свою карточку.
- **Проверка — отчётами компилятора и логом, а не на глаз**, и чинится только то, что они показали.

## Стилизованные компоненты и превью

- **Каждый стилизованный элемент берётся из `:core:designsystem`, `:shared:ui` или модуля `ui` фичи** (см. [Модули](modules.md#куда-класть-новый-код)); экран сам не стилизует компоненты Material.
- **Превью лежат рядом с тем, что показывают**, приватные, светлое и тёмное. Файл экрана показывает состояния, которые выглядят по-разному как экран целиком; состояния секции показываются в файле секции.
