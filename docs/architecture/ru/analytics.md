# Аналитика

[English version](../en/analytics.md) · [Все разделы](README.md)

Приложение отправляет события в две системы аналитики. Обе — заглушки, которые пишут в logcat, но код устроен так, как был бы с настоящими SDK.

## Путь события

```text
ViewModel ──log(event)──▶ Analytics ──▶ клиент каждой системы, которую назвало событие ──▶ SDK системы
```

| Часть | Где | Что делает |
|---|---|---|
| `AnalyticsEvent` | `:shared:analytics` | имя, типизированные параметры и системы, в которые идёт событие |
| `Analytics` | `:shared:analytics` | передаёт событие клиентам его систем |
| `AnalyticsSystem` | `:shared:analytics` | системы, которые использует приложение: `Insights` (продуктовая аналитика), `AdTracker` (реклама) |
| `AnalyticsSystemClient` | `:shared:analytics` | код, который отправляет в одну систему |
| `FakeInsightsClient`, `FakeAdTrackerClient` | `:apps:shop` (`analytics/`) | по клиенту на систему; заменяют SDK вроде Firebase Analytics и AppsFlyer |

## События

Каждое событие — класс, который сам называет свои системы:

```kotlin
internal class AddToCartAnalyticsEvent(
    productId: String,
    priceCents: Long,
    screen: AnalyticsScreen,
) : AnalyticsEvent("add_to_cart") {
    override val systems = setOf(AnalyticsSystem.Insights, AnalyticsSystem.AdTracker)

    override val params = analyticsParams {
        param("product_id", productId)
        param("price_cents", priceCents)
        param("screen", screen.value)
    }
}
```

- **Куда идёт событие, решает само событие.** На практике события добавляются часто, а системы меняются редко, и маршрут каждого события задаёт план трекинга; таблицу маршрутов в приложении пробовали и отказались.
- **Параметры типизированы** (`AnalyticsValue`: текст, число, флаг) — только типы, которые принимает любая система. Никакого `Map<String, Any>`.
- **Имена — явные строки**, поэтому переименование кода не меняет того, что получают системы.
- **Событие лежит в фиче, которая его отправляет** (`impl/…/analytics/`), или в `:shared:analytics` (`event/<тема>/`), если его отправляют две фичи и больше.

## Когда отправляются события

- **Только из ViewModel'ей и только после успеха действия**: «добавлено в корзину» пишется, когда Room сохранил товар, а не при нажатии.
- **Просмотры экранов отправляет приложение**, а не экраны ([`ScreenViews.kt`](../../../apps/shop/src/main/java/krio/systemdesign/shoppingapp/navigation/ScreenViews.kt)). Оно следит за стеком и сообщает о верхнем экране после каждого перехода и каждого возврата из фона. Каждая фича называет свои экраны в `NavDestination.xxxAnalyticsScreen()`; экран без имени не отправляется.

## Клиенты и сбои

- **Ровно один клиент на систему**, это проверяется при создании `Analytics`: иначе система без клиента молча теряла бы события, а система с двумя получала бы их дважды.
- **Упавший клиент не останавливает остальных**: его исключение пишется в лог, а событие всё равно уходит в другие системы.

## Что можно отправлять

- **Никакого свободного текста, который ввёл пользователь.** Поиск отправляет только длину запроса: в поле поиска может оказаться что угодно, имя или номер телефона.
- **Кроме отклонённых промокодов**: код отправляется как набран, потому что поле предназначено для коротких кодов, а узнать, какие несуществующие коды пробуют (старые акции, опечатки), — и есть смысл этого события.

## Чего нет намеренно

- **Нет модуля `:core:analytics`.** Список систем принадлежит этому приложению, поэтому события и `Analytics` лежат в `:shared:analytics`; то, что осталось бы в `core`, слишком мало для модуля.
- **Нет интерфейса `Analytics`.** Реализация одна; тест может передать записывающий клиент.
- **Нет ролей и меток событий** (продукт, маркетинг, реклама): событие напрямую называет свои системы.
