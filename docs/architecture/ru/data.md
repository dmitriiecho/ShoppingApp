# Данные

[English version](../en/data.md) · [Все разделы](README.md)

## Слои

| Где | Что |
|---|---|
| `:shared:domain` | модели, интерфейсы репозиториев и use case'ы, нужные двум фичам и больше; чистый Kotlin без Android |
| `:shared:data` | их реализации: Room, DataStore, API корзины; всё `internal` |
| `feature/<name>/impl/…/domain`, `…/data` | собственные модели, репозитории и use case'ы фичи (товары каталога, проверка промокода) |

ViewModel обращается к use case'ам, use case — к репозиторию, репозиторий — к Room, DataStore или серверу.

## Use case'ы

- **Use case — одно действие через репозиторий**: `AddToCartUseCase`, `ValidateCartUseCase`, `PlaceOrderUseCase`. Многие из них в одну строку; они есть для каждого действия, чтобы ViewModel никогда не зависела от репозитория.
- **Правила живут в моделях, а не в use case'ах**: итоги корзины в `Cart`, что нашла последняя проверка и что ещё не исправлено — в `CartValidation`, ограничение по остатку — в `canAddOneMore`.
- **Если имя обещает больше, чем делает код, к нему есть комментарий**: `PlaceOrderUseCase` только очищает корзину, потому что у сервера нет эндпоинта для заказов.

## Репозитории

- **Интерфейс репозитория говорит только на доменных моделях.** Entity Room и DTO сервера остаются внутри `data` и переводятся через `toDomain()` / `toEntity()`.
- **Репозиторий с одним источником работает с ним напрямую**: `ProductRepositoryImpl` вызывает `ProductApi`, `AppSettingsRepositoryImpl` — DataStore.
- **У корзины два источника**, и каждый — отдельный класс: [`LocalCartDataSource`](../../../shared/data/src/main/java/krio/systemdesign/shoppingapp/shared/data/source/LocalCartDataSource.kt) (Room: транзакции, слияние товара, который уже есть в корзине) и [`CartValidatorDataSource`](../../../shared/data/src/main/java/krio/systemdesign/shoppingapp/shared/data/source/CartValidatorDataSource.kt) (проверка на сервере). Репозиторий соединяет их и видит только доменные модели, а длинная логика Room живёт отдельно от сетевого кода. Интерфейсов у них нет: у каждого одна реализация.

## Результаты и ошибки

У каждой ошибки явный тип; никакой тип исключения не трактуется как то, чем он может не быть (`IOException` — это не «нет интернета»: его бросают и файлы).

| Операция | Что возвращает |
|---|---|
| либо удалась, либо нет, других исходов нет | `kotlin.Result<T>`: `CartRepository.addItem`, `getProducts` |
| есть исходы, которые не ошибки | собственный sealed-тип в модуле, которому принадлежит операция: `ProductLoadResult` (`Success` / `NotFound` / `Error`), `PromoCodeCheckResult`, `CartValidationResult` |

Исключения в эти результаты превращают две обёртки:

- **[`networkCall`](../../../core/network/src/main/java/krio/systemdesign/shoppingapp/core/network/NetworkResult.kt)** возвращает `NetworkResult`: `Success`, `HttpError` (сервер ответил кодом ошибки) или `Failure` (ответа нет или его не удалось прочитать). 4xx пишется в лог как предупреждение, потому что 404 на неизвестный промокод — нормальный ответ; 5xx и испорченные ответы — как ошибки.
- **[`databaseCall`](../../../shared/data/src/main/java/krio/systemdesign/shoppingapp/shared/data/database/DatabaseCall.kt)** ловит только `SQLiteException` (закончилось место, повреждён файл). Сработавший `require` — это баг: приложение падает, а не выдаёт его за ошибку базы.

Обе пропускают отмену корутины.

## Локальное хранение

| Хранилище | Что в нём |
|---|---|
| Room (`shopping.db`) | товары корзины и применённый промокод; схема экспортируется в `shared/data/schemas/` |
| DataStore Preferences | тема и задержка запросов из настроек |

Приложение ещё не выпущено, поэтому изменения схемы пока не требуют миграций: при изменении схемы debug-сборка пересоздаёт базу.

## Сеть

- **Один `OkHttpClient`** и для Retrofit, и для загрузки картинок через Coil: общие соединения и таймауты.
- **Перехватчики приходят из Hilt набором** (`@ApplicationInterceptor`), поэтому `:shared:data` добавляет задержку запросов, а `:core:network` о ней не знает. HTTP-лог добавляется только в debug.
- **Задержка запросов** из настроек ждёт перед каждым запросом к серверу, в том числе к картинкам, чтобы показать, как экраны ведут себя при ожидании.
- **Обычный HTTP разрешён только для адреса сервера** (`network_security_config.xml`): у него нет домена, а значит, и HTTPS.

## Цены

- **Все цены в долларах США, числом центов типа `Long`**: `14999` — это $149.99. Те же числа в JSON сервера, DTO, Room и доменных моделях.
- **Показываются только через [`formatPrice`](../../../shared/ui/src/main/java/krio/systemdesign/shoppingapp/shared/ui/text/PriceFormat.kt)**: «$1,234.56» при любом языке телефона.
- **Value class `Money` нет.** Он мог бы жить только в домене: `:shared:ui` принимает простые значения, а доменный тип в UI state был бы нестабилен для Compose. Большая часть кода с ценами — это UI, так что тип защищал бы немногое; его стоит вводить вместе со второй валютой или налогами.

## Договорённости с сервером

API и правила данных сервера описаны в [`server/README.ru.md`](../../../server/README.ru.md). Приложение рассчитывает на следующее:

- **DTO — копии серверных**, с комментарием, указывающим на другую сторону.
- **Пагинация по номеру страницы безопасна**: сервер никогда не удаляет товары и добавляет новые в конец. Переименованный товар всё же может сдвинуться в результатах поиска, поэтому `ProductPagingSource` отбрасывает повторяющиеся id.
- **Открыть ли оформление, решает сервер.** Корзина показывает, что нашла её последняя проверка, но «Оформить» открывает оформление только после свежего `Success` от сервера.
- **Процент скидки промокода никогда не меняется**, поэтому сервер проверяет только, что код ещё существует.
- **Тестовые пункты настроек рассчитывают на четыре товара**, которые сохраняют свой остаток и цену; их проверяет тест сервера.
